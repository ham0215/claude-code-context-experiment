## Dataclasses and attrs

### Dataclass Inheritance Guidelines

This section covers the conventions and best practices for dataclass inheritance guidelines
within the broader context of Python dataclass and attrs usage conventions for structured data modeling, immutability, and validation patterns. Following these guidelines ensures
consistency across the codebase and reduces the likelihood of common errors.

Understanding dataclass inheritance guidelines is essential for maintaining high-quality Python
code in our projects. The patterns described here have been refined through
extensive use in production systems and reflect industry best practices adapted
to our specific needs.

#### Guidelines for Dataclass Inheritance Guidelines

The following guidelines govern how dataclass inheritance guidelines should be implemented and maintained in this project:

1. **Rule 1**: Use `frozen=True` for value objects that should be immutable after creation
2. **Rule 2**: Define default values using `field(default_factory=...)` for mutable defaults
3. **Rule 3**: Use `__post_init__` for derived field computation and validation
4. **Rule 4**: Prefer `slots=True` for memory-efficient dataclasses in Python 3.10+
5. **Rule 5**: Use attrs `@define` decorator for classes requiring complex validation
6. **Rule 6**: Keep dataclass fields ordered: required fields first, then optional with defaults
7. **Rule 7**: Use `asdict()` and `astuple()` for serialization rather than custom methods

    #### Code Example

    The following example demonstrates the recommended pattern for
    dataclass inheritance guidelines:

    ```python
    def with_dataclass_inheritance_guidelin(
    retries: int = 3,
    backoff_factor: float = 0.5,
) -> Callable[[F], F]:
    """Decorator to apply dataclass inheritance guidelines conventions.

    Wraps a function with retry logic and logging following
    the project's dataclasses and attrs standards.

    Args:
        retries: Maximum number of retry attempts.
        backoff_factor: Multiplier for exponential backoff delay.

    Returns:
        Decorated function with retry behavior.
    """
    def decorator(func: F) -> F:
        @functools.wraps(func)
        def wrapper(*args: Any, **kwargs: Any) -> Any:
            logger = logging.getLogger(func.__module__)
            last_exception: Exception | None = None
            for attempt in range(1, retries + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as exc:
                    last_exception = exc
                    delay = backoff_factor * (2 ** (attempt - 1))
                    logger.warning(
                        "%s attempt %d/%d failed: %s (retry in %.1fs)",
                        func.__name__, attempt, retries, exc, delay,
                    )
                    time.sleep(delay)
            raise RuntimeError(
                f"{func.__name__} failed after {retries} attempts"
            ) from last_exception
        return wrapper  # type: ignore[return-value]
    return decorator
    ```

    **Explanation**: This example follows our project conventions by using
    explicit type annotations, comprehensive docstrings, and proper error
    handling. Note the use of logging instead of print statements, and the
    structured return types that facilitate downstream processing.

#### Best Practices

When working with dataclass inheritance guidelines in the context of dataclasses and attrs, keep these practices in mind:

- Use `frozen=True` for value objects that should be immutable after creation
- Define default values using `field(default_factory=...)` for mutable defaults
- Use `__post_init__` for derived field computation and validation
- Prefer `slots=True` for memory-efficient dataclasses in Python 3.10+

These practices help maintain code quality and reduce the risk of introducing bugs or performance issues related to dataclass inheritance guidelines.

#### Common Anti-Patterns

Avoid the following anti-patterns when implementing dataclass inheritance guidelines:

- **Ignoring error conditions**: Always handle potential failures explicitly
  rather than silently swallowing exceptions or returning None.
- **Missing documentation**: Every public function and class must have a
  docstring explaining its purpose, parameters, and return value.
- **Hardcoded configuration**: Extract configuration values into environment
  variables or configuration files rather than embedding them in code.
- **Insufficient testing**: Write tests that cover both the happy path and
  edge cases, including error conditions and boundary values.

These anti-patterns are commonly encountered during code reviews and should
be addressed before merging any changes related to dataclasses and attrs.

#### Integration Notes

When integrating dataclass inheritance guidelines into existing code, ensure that
the surrounding code follows the same conventions described in this
section. Consistency is more important than any individual rule, so
when in doubt, follow the established patterns in the immediate
codebase context.
