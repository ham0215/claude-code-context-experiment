## Flask/FastAPI Routing

### WebSocket Endpoint Design

This section covers the conventions and best practices for websocket endpoint design
within the broader context of web framework routing conventions for Flask and FastAPI, including endpoint design, middleware, and request handling. Following these guidelines ensures
consistency across the codebase and reduces the likelihood of common errors.

Understanding websocket endpoint design is essential for maintaining high-quality Python
code in our projects. The patterns described here have been refined through
extensive use in production systems and reflect industry best practices adapted
to our specific needs.

#### Guidelines for WebSocket Endpoint Design

The following guidelines govern how websocket endpoint design should be implemented and maintained in this project:

1. **Rule 1**: Use plural nouns for resource endpoints (e.g., `/users`, `/orders`)
2. **Rule 2**: Return consistent error response structures with `detail` and `status_code`
3. **Rule 3**: Validate all request bodies using Pydantic models or marshmallow schemas
4. **Rule 4**: Group related endpoints into blueprints or routers by domain
5. **Rule 5**: Use dependency injection for shared resources like database sessions
6. **Rule 6**: Apply rate limiting middleware to public-facing endpoints
7. **Rule 7**: Document all endpoints with OpenAPI-compatible docstrings

#### Best Practices

When working with websocket endpoint design in the context of flask/fastapi routing, keep these practices in mind:

- Use plural nouns for resource endpoints (e.g., `/users`, `/orders`)
- Return consistent error response structures with `detail` and `status_code`
- Validate all request bodies using Pydantic models or marshmallow schemas
- Group related endpoints into blueprints or routers by domain

These practices help maintain code quality and reduce the risk of introducing bugs or performance issues related to websocket endpoint design.

#### Common Anti-Patterns

Avoid the following anti-patterns when implementing websocket endpoint design:

- **Ignoring error conditions**: Always handle potential failures explicitly
  rather than silently swallowing exceptions or returning None.
- **Missing documentation**: Every public function and class must have a
  docstring explaining its purpose, parameters, and return value.
- **Hardcoded configuration**: Extract configuration values into environment
  variables or configuration files rather than embedding them in code.
- **Insufficient testing**: Write tests that cover both the happy path and
  edge cases, including error conditions and boundary values.

These anti-patterns are commonly encountered during code reviews and should
be addressed before merging any changes related to flask/fastapi routing.
