## Performance Optimization

### Collection Type Selection

This section covers the conventions and best practices for collection type selection
within the broader context of Python performance optimization techniques including profiling, caching, algorithmic improvements, and memory management. Following these guidelines ensures
consistency across the codebase and reduces the likelihood of common errors.

Understanding collection type selection is essential for maintaining high-quality Python
code in our projects. The patterns described here have been refined through
extensive use in production systems and reflect industry best practices adapted
to our specific needs.

#### Guidelines for Collection Type Selection

The following guidelines govern how collection type selection should be implemented and maintained in this project:

1. **Rule 1**: Profile before optimizing; use `cProfile` or `py-spy` to identify actual bottlenecks
2. **Rule 2**: Use `functools.lru_cache` for expensive pure functions with hashable arguments
3. **Rule 3**: Prefer generators over lists for large sequences that are consumed once
4. **Rule 4**: Choose appropriate data structures: `set` for membership testing, `deque` for queue operations
5. **Rule 5**: Use `str.join()` for concatenating many strings instead of repeated `+` operations
6. **Rule 6**: Avoid premature optimization; focus on algorithmic complexity first
7. **Rule 7**: Use `__slots__` on classes instantiated in large quantities to reduce memory overhead

    #### Code Example

    The following example demonstrates the recommended pattern for
    collection type selection:

    ```python
    def with_collection_type_selection(
    retries: int = 3,
    backoff_factor: float = 0.5,
) -> Callable[[F], F]:
    """Decorator to apply collection type selection conventions.

    Wraps a function with retry logic and logging following
    the project's performance optimization standards.

    Args:
        retries: Maximum number of retry attempts.
        backoff_factor: Multiplier for exponential backoff delay.

    Returns:
        Decorated function with retry behavior.
    """
    def decorator(func: F) -> F:
        @functools.wraps(func)
        def wrapper(*args: Any, **kwargs: Any) -> Any:
            logger = logging.getLogger(func.__module__)
            last_exception: Exception | None = None
            for attempt in range(1, retries + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as exc:
                    last_exception = exc
                    delay = backoff_factor * (2 ** (attempt - 1))
                    logger.warning(
                        "%s attempt %d/%d failed: %s (retry in %.1fs)",
                        func.__name__, attempt, retries, exc, delay,
                    )
                    time.sleep(delay)
            raise RuntimeError(
                f"{func.__name__} failed after {retries} attempts"
            ) from last_exception
        return wrapper  # type: ignore[return-value]
    return decorator
    ```

    **Explanation**: This example follows our project conventions by using
    explicit type annotations, comprehensive docstrings, and proper error
    handling. Note the use of logging instead of print statements, and the
    structured return types that facilitate downstream processing.

#### Best Practices

When working with collection type selection in the context of performance optimization, keep these practices in mind:

- Profile before optimizing; use `cProfile` or `py-spy` to identify actual bottlenecks
- Use `functools.lru_cache` for expensive pure functions with hashable arguments
- Prefer generators over lists for large sequences that are consumed once
- Choose appropriate data structures: `set` for membership testing, `deque` for queue operations

These practices help maintain code quality and reduce the risk of introducing bugs or performance issues related to collection type selection.

#### Common Anti-Patterns

Avoid the following anti-patterns when implementing collection type selection:

- **Ignoring error conditions**: Always handle potential failures explicitly
  rather than silently swallowing exceptions or returning None.
- **Missing documentation**: Every public function and class must have a
  docstring explaining its purpose, parameters, and return value.
- **Hardcoded configuration**: Extract configuration values into environment
  variables or configuration files rather than embedding them in code.
- **Insufficient testing**: Write tests that cover both the happy path and
  edge cases, including error conditions and boundary values.

These anti-patterns are commonly encountered during code reviews and should
be addressed before merging any changes related to performance optimization.

#### Integration Notes

When integrating collection type selection into existing code, ensure that
the surrounding code follows the same conventions described in this
section. Consistency is more important than any individual rule, so
when in doubt, follow the established patterns in the immediate
codebase context.
