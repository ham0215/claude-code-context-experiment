## Flask/FastAPI Routing

### Error Response Standardization

This section covers the conventions and best practices for error response standardization
within the broader context of web framework routing conventions for Flask and FastAPI, including endpoint design, middleware, and request handling. Following these guidelines ensures
consistency across the codebase and reduces the likelihood of common errors.

Understanding error response standardization is essential for maintaining high-quality Python
code in our projects. The patterns described here have been refined through
extensive use in production systems and reflect industry best practices adapted
to our specific needs.

#### Guidelines for Error Response Standardization

The following guidelines govern how error response standardization should be implemented and maintained in this project:

1. **Rule 1**: Use plural nouns for resource endpoints (e.g., `/users`, `/orders`)
2. **Rule 2**: Return consistent error response structures with `detail` and `status_code`
3. **Rule 3**: Validate all request bodies using Pydantic models or marshmallow schemas
4. **Rule 4**: Group related endpoints into blueprints or routers by domain
5. **Rule 5**: Use dependency injection for shared resources like database sessions
6. **Rule 6**: Apply rate limiting middleware to public-facing endpoints
7. **Rule 7**: Document all endpoints with OpenAPI-compatible docstrings

    #### Code Example

    The following example demonstrates the recommended pattern for
    error response standardization:

    ```python
    def with_error_response_standardization(
    retries: int = 3,
    backoff_factor: float = 0.5,
) -> Callable[[F], F]:
    """Decorator to apply error response standardization conventions.

    Wraps a function with retry logic and logging following
    the project's flask/fastapi routing standards.

    Args:
        retries: Maximum number of retry attempts.
        backoff_factor: Multiplier for exponential backoff delay.

    Returns:
        Decorated function with retry behavior.
    """
    def decorator(func: F) -> F:
        @functools.wraps(func)
        def wrapper(*args: Any, **kwargs: Any) -> Any:
            logger = logging.getLogger(func.__module__)
            last_exception: Exception | None = None
            for attempt in range(1, retries + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as exc:
                    last_exception = exc
                    delay = backoff_factor * (2 ** (attempt - 1))
                    logger.warning(
                        "%s attempt %d/%d failed: %s (retry in %.1fs)",
                        func.__name__, attempt, retries, exc, delay,
                    )
                    time.sleep(delay)
            raise RuntimeError(
                f"{func.__name__} failed after {retries} attempts"
            ) from last_exception
        return wrapper  # type: ignore[return-value]
    return decorator
    ```

    **Explanation**: This example follows our project conventions by using
    explicit type annotations, comprehensive docstrings, and proper error
    handling. Note the use of logging instead of print statements, and the
    structured return types that facilitate downstream processing.

#### Best Practices

When working with error response standardization in the context of flask/fastapi routing, keep these practices in mind:

- Use plural nouns for resource endpoints (e.g., `/users`, `/orders`)
- Return consistent error response structures with `detail` and `status_code`
- Validate all request bodies using Pydantic models or marshmallow schemas
- Group related endpoints into blueprints or routers by domain

These practices help maintain code quality and reduce the risk of introducing bugs or performance issues related to error response standardization.

#### Common Anti-Patterns

Avoid the following anti-patterns when implementing error response standardization:

- **Ignoring error conditions**: Always handle potential failures explicitly
  rather than silently swallowing exceptions or returning None.
- **Missing documentation**: Every public function and class must have a
  docstring explaining its purpose, parameters, and return value.
- **Hardcoded configuration**: Extract configuration values into environment
  variables or configuration files rather than embedding them in code.
- **Insufficient testing**: Write tests that cover both the happy path and
  edge cases, including error conditions and boundary values.

These anti-patterns are commonly encountered during code reviews and should
be addressed before merging any changes related to flask/fastapi routing.

#### Integration Notes

When integrating error response standardization into existing code, ensure that
the surrounding code follows the same conventions described in this
section. Consistency is more important than any individual rule, so
when in doubt, follow the established patterns in the immediate
codebase context.
