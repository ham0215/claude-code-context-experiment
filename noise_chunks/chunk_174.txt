## Configuration Management

### Feature Flag Patterns

This section covers the conventions and best practices for feature flag patterns
within the broader context of Python application configuration patterns using pydantic-settings, environment variables, and hierarchical config systems. Following these guidelines ensures
consistency across the codebase and reduces the likelihood of common errors.

Understanding feature flag patterns is essential for maintaining high-quality Python
code in our projects. The patterns described here have been refined through
extensive use in production systems and reflect industry best practices adapted
to our specific needs.

#### Guidelines for Feature Flag Patterns

The following guidelines govern how feature flag patterns should be implemented and maintained in this project:

1. **Rule 1**: Use pydantic `BaseSettings` for type-safe configuration with environment variable support
2. **Rule 2**: Prefix all application environment variables with a project-specific namespace
3. **Rule 3**: Validate configuration eagerly at application startup, not at first use
4. **Rule 4**: Separate secret configuration (credentials) from non-secret settings
5. **Rule 5**: Provide sensible defaults for all non-secret configuration values
6. **Rule 6**: Document all configuration options with `Field(description=...)`
7. **Rule 7**: Use `.env` files for local development only; never commit them to version control

    #### Code Example

    The following example demonstrates the recommended pattern for
    feature flag patterns:

    ```python
    @dataclass(frozen=True, slots=True)
class FeatureFlagPatternsConfig:
    """Configuration for feature flag patterns.

    Follows the project's configuration management conventions
    for immutable configuration objects.
    """
    name: str
    enabled: bool = True
    max_items: int = 100
    timeout_seconds: float = 30.0
    tags: tuple[str, ...] = ()

    def __post_init__(self) -> None:
        """Validate configuration values."""
        if self.max_items <= 0:
            raise ValueError("max_items must be positive")
        if self.timeout_seconds <= 0:
            raise ValueError("timeout_seconds must be positive")

    @classmethod
    def from_env(cls, prefix: str = "FEATURE_FLAG_PATTERNS") -> "FeatureFlagPatternsConfig":
        """Create configuration from environment variables.

        Args:
            prefix: Environment variable prefix.

        Returns:
            Configured instance.
        """
        import os
        return cls(
            name=os.environ.get(f"{prefix}_NAME", "default"),
            enabled=os.environ.get(f"{prefix}_ENABLED", "true").lower() == "true",
            max_items=int(os.environ.get(f"{prefix}_MAX_ITEMS", "100")),
            timeout_seconds=float(os.environ.get(f"{prefix}_TIMEOUT", "30.0")),
        )
    ```

    **Explanation**: This example follows our project conventions by using
    explicit type annotations, comprehensive docstrings, and proper error
    handling. Note the use of logging instead of print statements, and the
    structured return types that facilitate downstream processing.

#### Best Practices

When working with feature flag patterns in the context of configuration management, keep these practices in mind:

- Use pydantic `BaseSettings` for type-safe configuration with environment variable support
- Prefix all application environment variables with a project-specific namespace
- Validate configuration eagerly at application startup, not at first use
- Separate secret configuration (credentials) from non-secret settings

These practices help maintain code quality and reduce the risk of introducing bugs or performance issues related to feature flag patterns.

#### Common Anti-Patterns

Avoid the following anti-patterns when implementing feature flag patterns:

- **Ignoring error conditions**: Always handle potential failures explicitly
  rather than silently swallowing exceptions or returning None.
- **Missing documentation**: Every public function and class must have a
  docstring explaining its purpose, parameters, and return value.
- **Hardcoded configuration**: Extract configuration values into environment
  variables or configuration files rather than embedding them in code.
- **Insufficient testing**: Write tests that cover both the happy path and
  edge cases, including error conditions and boundary values.

These anti-patterns are commonly encountered during code reviews and should
be addressed before merging any changes related to configuration management.

#### Integration Notes

When integrating feature flag patterns into existing code, ensure that
the surrounding code follows the same conventions described in this
section. Consistency is more important than any individual rule, so
when in doubt, follow the established patterns in the immediate
codebase context.

The conventions described here apply specifically to Python application configuration patterns using pydantic-settings, environment variables, and hierarchical config systems.
Other areas of the codebase may have different conventions that are
documented in their respective sections.
