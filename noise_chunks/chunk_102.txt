## Exception Handling Patterns

### Context Manager Error Handling

This section covers the conventions and best practices for context manager error handling
within the broader context of Python exception handling conventions including custom exception hierarchies, error propagation, and recovery strategies. Following these guidelines ensures
consistency across the codebase and reduces the likelihood of common errors.

Understanding context manager error handling is essential for maintaining high-quality Python
code in our projects. The patterns described here have been refined through
extensive use in production systems and reflect industry best practices adapted
to our specific needs.

#### Guidelines for Context Manager Error Handling

The following guidelines govern how context manager error handling should be implemented and maintained in this project:

1. **Rule 1**: Define a project-level base exception class that all custom exceptions inherit from
2. **Rule 2**: Use `raise ... from ...` for exception chaining to preserve the original traceback
3. **Rule 3**: Never use bare `except:` clauses; always specify the exception type
4. **Rule 4**: Catch specific exceptions rather than broad `Exception` unless re-raising
5. **Rule 5**: Include relevant context data in custom exception attributes
6. **Rule 6**: Log exceptions at the handler level, not at the raise site
7. **Rule 7**: Use `contextlib.suppress` for expected exceptions that need no handling

    #### Code Example

    The following example demonstrates the recommended pattern for
    context manager error handling:

    ```python
    @contextmanager
def context_manager_error_handling_context(
    resource_id: str,
    options: dict[str, Any] | None = None,
) -> Generator[ContextManagerErrorHandlingSession, None, None]:
    """Create a managed context for context manager error handling.

    Ensures proper resource acquisition and cleanup following
    the project's exception handling patterns conventions.

    Args:
        resource_id: Identifier for the resource to manage.
        options: Optional configuration overrides.

    Yields:
        A configured session object.
    """
    options = options or {}
    logger = logging.getLogger(__name__)
    logger.debug("Acquiring context_manager_error_handling resource: %s", resource_id)

    session = ContextManagerErrorHandlingSession(resource_id, **options)
    try:
        session.initialize()
        yield session
    except Exception:
        logger.exception("Error in context_manager_error_handling context")
        raise
    finally:
        session.cleanup()
        logger.debug("Released context_manager_error_handling resource: %s", resource_id)
    ```

    **Explanation**: This example follows our project conventions by using
    explicit type annotations, comprehensive docstrings, and proper error
    handling. Note the use of logging instead of print statements, and the
    structured return types that facilitate downstream processing.

#### Best Practices

When working with context manager error handling in the context of exception handling patterns, keep these practices in mind:

- Define a project-level base exception class that all custom exceptions inherit from
- Use `raise ... from ...` for exception chaining to preserve the original traceback
- Never use bare `except:` clauses; always specify the exception type
- Catch specific exceptions rather than broad `Exception` unless re-raising

These practices help maintain code quality and reduce the risk of introducing bugs or performance issues related to context manager error handling.

#### Common Anti-Patterns

Avoid the following anti-patterns when implementing context manager error handling:

- **Ignoring error conditions**: Always handle potential failures explicitly
  rather than silently swallowing exceptions or returning None.
- **Missing documentation**: Every public function and class must have a
  docstring explaining its purpose, parameters, and return value.
- **Hardcoded configuration**: Extract configuration values into environment
  variables or configuration files rather than embedding them in code.
- **Insufficient testing**: Write tests that cover both the happy path and
  edge cases, including error conditions and boundary values.

These anti-patterns are commonly encountered during code reviews and should
be addressed before merging any changes related to exception handling patterns.
