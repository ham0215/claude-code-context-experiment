## CI/CD Python Configuration

### GitHub Actions Workflow Design

This section covers the conventions and best practices for github actions workflow design
within the broader context of continuous integration and deployment pipeline configuration for Python projects, including testing, linting, and release automation. Following these guidelines ensures
consistency across the codebase and reduces the likelihood of common errors.

Understanding github actions workflow design is essential for maintaining high-quality Python
code in our projects. The patterns described here have been refined through
extensive use in production systems and reflect industry best practices adapted
to our specific needs.

#### Guidelines for GitHub Actions Workflow Design

The following guidelines govern how github actions workflow design should be implemented and maintained in this project:

1. **Rule 1**: Run linting, type checking, and tests as separate CI jobs for clear failure attribution
2. **Rule 2**: Test against all supported Python versions using matrix builds
3. **Rule 3**: Cache pip downloads and virtual environments to speed up CI runs
4. **Rule 4**: Use `--fail-fast` in CI to abort early on critical failures
5. **Rule 5**: Pin CI action versions to specific SHA hashes for security
6. **Rule 6**: Separate CI workflows for pull requests and main branch pushes
7. **Rule 7**: Store secrets in CI platform secret management, never in repository files

#### Best Practices

When working with github actions workflow design in the context of ci/cd python configuration, keep these practices in mind:

- Run linting, type checking, and tests as separate CI jobs for clear failure attribution
- Test against all supported Python versions using matrix builds
- Cache pip downloads and virtual environments to speed up CI runs
- Use `--fail-fast` in CI to abort early on critical failures

These practices help maintain code quality and reduce the risk of introducing bugs or performance issues related to github actions workflow design.

#### Common Anti-Patterns

Avoid the following anti-patterns when implementing github actions workflow design:

- **Ignoring error conditions**: Always handle potential failures explicitly
  rather than silently swallowing exceptions or returning None.
- **Missing documentation**: Every public function and class must have a
  docstring explaining its purpose, parameters, and return value.
- **Hardcoded configuration**: Extract configuration values into environment
  variables or configuration files rather than embedding them in code.
- **Insufficient testing**: Write tests that cover both the happy path and
  edge cases, including error conditions and boundary values.

These anti-patterns are commonly encountered during code reviews and should
be addressed before merging any changes related to ci/cd python configuration.
