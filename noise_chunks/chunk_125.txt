## Concurrent Processing

### Future and Callback Patterns

This section covers the conventions and best practices for future and callback patterns
within the broader context of Python concurrency patterns using threading, multiprocessing, and concurrent.futures for parallel task execution. Following these guidelines ensures
consistency across the codebase and reduces the likelihood of common errors.

Understanding future and callback patterns is essential for maintaining high-quality Python
code in our projects. The patterns described here have been refined through
extensive use in production systems and reflect industry best practices adapted
to our specific needs.

#### Guidelines for Future and Callback Patterns

The following guidelines govern how future and callback patterns should be implemented and maintained in this project:

1. **Rule 1**: Use `concurrent.futures` for high-level parallel execution instead of raw threads
2. **Rule 2**: Choose `ThreadPoolExecutor` for I/O-bound and `ProcessPoolExecutor` for CPU-bound work
3. **Rule 3**: Always use context managers (`with`) when creating executor instances
4. **Rule 4**: Limit thread pool size to avoid resource exhaustion; default to `min(32, os.cpu_count() + 4)`
5. **Rule 5**: Use `threading.Lock` to protect shared mutable state across threads
6. **Rule 6**: Handle `KeyboardInterrupt` in concurrent code for clean shutdown
7. **Rule 7**: Prefer immutable data when communicating between threads or processes

    #### Code Example

    The following example demonstrates the recommended pattern for
    future and callback patterns:

    ```python
    def with_future_and_callback_patterns(
    retries: int = 3,
    backoff_factor: float = 0.5,
) -> Callable[[F], F]:
    """Decorator to apply future and callback patterns conventions.

    Wraps a function with retry logic and logging following
    the project's concurrent processing standards.

    Args:
        retries: Maximum number of retry attempts.
        backoff_factor: Multiplier for exponential backoff delay.

    Returns:
        Decorated function with retry behavior.
    """
    def decorator(func: F) -> F:
        @functools.wraps(func)
        def wrapper(*args: Any, **kwargs: Any) -> Any:
            logger = logging.getLogger(func.__module__)
            last_exception: Exception | None = None
            for attempt in range(1, retries + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as exc:
                    last_exception = exc
                    delay = backoff_factor * (2 ** (attempt - 1))
                    logger.warning(
                        "%s attempt %d/%d failed: %s (retry in %.1fs)",
                        func.__name__, attempt, retries, exc, delay,
                    )
                    time.sleep(delay)
            raise RuntimeError(
                f"{func.__name__} failed after {retries} attempts"
            ) from last_exception
        return wrapper  # type: ignore[return-value]
    return decorator
    ```

    **Explanation**: This example follows our project conventions by using
    explicit type annotations, comprehensive docstrings, and proper error
    handling. Note the use of logging instead of print statements, and the
    structured return types that facilitate downstream processing.

#### Best Practices

When working with future and callback patterns in the context of concurrent processing, keep these practices in mind:

- Use `concurrent.futures` for high-level parallel execution instead of raw threads
- Choose `ThreadPoolExecutor` for I/O-bound and `ProcessPoolExecutor` for CPU-bound work
- Always use context managers (`with`) when creating executor instances
- Limit thread pool size to avoid resource exhaustion; default to `min(32, os.cpu_count() + 4)`

These practices help maintain code quality and reduce the risk of introducing bugs or performance issues related to future and callback patterns.

#### Common Anti-Patterns

Avoid the following anti-patterns when implementing future and callback patterns:

- **Ignoring error conditions**: Always handle potential failures explicitly
  rather than silently swallowing exceptions or returning None.
- **Missing documentation**: Every public function and class must have a
  docstring explaining its purpose, parameters, and return value.
- **Hardcoded configuration**: Extract configuration values into environment
  variables or configuration files rather than embedding them in code.
- **Insufficient testing**: Write tests that cover both the happy path and
  edge cases, including error conditions and boundary values.

These anti-patterns are commonly encountered during code reviews and should
be addressed before merging any changes related to concurrent processing.

#### Integration Notes

When integrating future and callback patterns into existing code, ensure that
the surrounding code follows the same conventions described in this
section. Consistency is more important than any individual rule, so
when in doubt, follow the established patterns in the immediate
codebase context.
