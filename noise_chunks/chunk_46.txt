## Logging Best Practices

### Third-Party Log Integration

This section covers the conventions and best practices for third-party log integration
within the broader context of Python logging configuration, structured logging patterns, and observability conventions for production applications. Following these guidelines ensures
consistency across the codebase and reduces the likelihood of common errors.

Understanding third-party log integration is essential for maintaining high-quality Python
code in our projects. The patterns described here have been refined through
extensive use in production systems and reflect industry best practices adapted
to our specific needs.

#### Guidelines for Third-Party Log Integration

The following guidelines govern how third-party log integration should be implemented and maintained in this project:

1. **Rule 1**: Use `logging.getLogger(__name__)` to create module-level loggers
2. **Rule 2**: Never use `print()` for application logging in production code
3. **Rule 3**: Include correlation IDs in all log messages for request tracing
4. **Rule 4**: Use lazy formatting with `%s` placeholders instead of f-strings in log calls
5. **Rule 5**: Configure log levels per environment: DEBUG for dev, WARNING for production
6. **Rule 6**: Structure log output as JSON for machine-parseable log aggregation
7. **Rule 7**: Never log sensitive data such as passwords, tokens, or PII

#### Code Example

The following example demonstrates the recommended pattern for
third-party log integration:

```python
class ThirdpartyLogIntegrationHandler:
"""Handle third-party log integration operations.

Implements the standard patterns for logging best practices
as defined in our project conventions.
"""

def __init__(self, config: dict[str, Any]) -> None:
    self._config = config
    self._logger = logging.getLogger(__name__)

def process(self, data: Any) -> dict[str, Any]:
    """Process data according to third-party log integration conventions.

    Args:
        data: Input data to process.

    Returns:
        Processed result dictionary.

    Raises:
        ValueError: If data is invalid.
    """
    self._validate(data)
    result = self._transform(data)
    self._logger.info("Processed %d items", len(result))
    return result

def _validate(self, data: Any) -> None:
    """Validate input data."""
    if not data:
        raise ValueError("Input data must not be empty")

def _transform(self, data: Any) -> dict[str, Any]:
    """Apply transformation logic."""
    return {"status": "processed", "items": data}
```

**Explanation**: This example follows our project conventions by using
explicit type annotations, comprehensive docstrings, and proper error
handling. Note the use of logging instead of print statements, and the
structured return types that facilitate downstream processing.

#### Best Practices

When working with third-party log integration in the context of logging best practices, keep these practices in mind:

- Use `logging.getLogger(__name__)` to create module-level loggers
- Never use `print()` for application logging in production code
- Include correlation IDs in all log messages for request tracing
- Use lazy formatting with `%s` placeholders instead of f-strings in log calls

These practices help maintain code quality and reduce the risk of introducing bugs or performance issues related to third-party log integration.

#### Common Anti-Patterns

Avoid the following anti-patterns when implementing third-party log integration:

- **Ignoring error conditions**: Always handle potential failures explicitly
  rather than silently swallowing exceptions or returning None.
- **Missing documentation**: Every public function and class must have a
  docstring explaining its purpose, parameters, and return value.
- **Hardcoded configuration**: Extract configuration values into environment
  variables or configuration files rather than embedding them in code.
- **Insufficient testing**: Write tests that cover both the happy path and
  edge cases, including error conditions and boundary values.

These anti-patterns are commonly encountered during code reviews and should
be addressed before merging any changes related to logging best practices.

#### Integration Notes

When integrating third-party log integration into existing code, ensure that
the surrounding code follows the same conventions described in this
section. Consistency is more important than any individual rule, so
when in doubt, follow the established patterns in the immediate
codebase context.

The conventions described here apply specifically to Python logging configuration, structured logging patterns, and observability conventions for production applications.
Other areas of the codebase may have different conventions that are
documented in their respective sections.
