consistency across the codebase and reduces the likelihood of common errors.

#### Guidelines for ASGI Server Configuration (Uvicorn)

The following guidelines govern how asgi server configuration (uvicorn) should be implemented and maintained in this project:

1. **Rule 1**: Use multi-stage Docker builds to minimize final image size
2. **Rule 2**: Run Python applications as non-root users inside containers
3. **Rule 3**: Set `--workers` based on CPU count: `2 * CPU + 1` for Gunicorn
4. **Rule 4**: Implement `/health` and `/ready` endpoints for orchestrator probes
5. **Rule 5**: Handle SIGTERM gracefully to allow in-flight requests to complete
6. **Rule 6**: Use `.dockerignore` to exclude test files, docs, and development artifacts
7. **Rule 7**: Pin base image versions to specific digests for reproducible builds

#### Best Practices

When working with asgi server configuration (uvicorn) in the context of deployment patterns, keep these practices in mind:

- Use multi-stage Docker builds to minimize final image size
- Run Python applications as non-root users inside containers
- Set `--workers` based on CPU count: `2 * CPU + 1` for Gunicorn
- Implement `/health` and `/ready` endpoints for orchestrator probes

These practices help maintain code quality and reduce the risk of introducing bugs or performance issues related to asgi server configuration (uvicorn).

#### Common Anti-Patterns

Avoid the following anti-patterns when implementing asgi server configuration (uvicorn):

- **Ignoring error conditions**: Always handle potential failures explicitly
  rather than silently swallowing exceptions or returning None.
- **Missing documentation**: Every public function and class must have a
  docstring explaining its purpose, parameters, and return value.
- **Hardcoded configuration**: Extract configuration values into environment
  variables or configuration files rather than embedding them in code.
- **Insufficient testing**: Write tests that cover both the happy path and
  edge cases, including error conditions and boundary values.

These anti-patterns are commonly encountered during code reviews and should
be addressed before merging any changes related to deployment patterns.
