## Advanced Type Hints

### TypeGuard and Type Narrowing

This section covers the conventions and best practices for typeguard and type narrowing
within the broader context of advanced Python type annotation patterns using Protocol, TypeVar, Generic, and other typing constructs for expressive static analysis. Following these guidelines ensures
consistency across the codebase and reduces the likelihood of common errors.

Understanding typeguard and type narrowing is essential for maintaining high-quality Python
code in our projects. The patterns described here have been refined through
extensive use in production systems and reflect industry best practices adapted
to our specific needs.

#### Guidelines for TypeGuard and Type Narrowing

The following guidelines govern how typeguard and type narrowing should be implemented and maintained in this project:

1. **Rule 1**: Use `Protocol` for structural subtyping instead of abstract base classes where possible
2. **Rule 2**: Define `TypeVar` with meaningful names that indicate the constraint (e.g., `UserT`, `ResponseT`)
3. **Rule 3**: Prefer `Sequence` over `list` in function signatures for input parameters
4. **Rule 4**: Use `TypeGuard` to help type checkers understand custom type narrowing functions
5. **Rule 5**: Apply `@overload` to functions with different return types based on input types
6. **Rule 6**: Use `Final` for constants that should not be reassigned
7. **Rule 7**: Run `mypy --strict` in CI to catch type errors early

    #### Code Example

    The following example demonstrates the recommended pattern for
    typeguard and type narrowing:

    ```python
    @dataclass(frozen=True, slots=True)
class TypeguardAndTypeNarrowingConfig:
    """Configuration for typeguard and type narrowing.

    Follows the project's advanced type hints conventions
    for immutable configuration objects.
    """
    name: str
    enabled: bool = True
    max_items: int = 100
    timeout_seconds: float = 30.0
    tags: tuple[str, ...] = ()

    def __post_init__(self) -> None:
        """Validate configuration values."""
        if self.max_items <= 0:
            raise ValueError("max_items must be positive")
        if self.timeout_seconds <= 0:
            raise ValueError("timeout_seconds must be positive")

    @classmethod
    def from_env(cls, prefix: str = "TYPEGUARD_AND_TYPE_NARROWING") -> "TypeguardAndTypeNarrowingConfig":
        """Create configuration from environment variables.

        Args:
            prefix: Environment variable prefix.

        Returns:
            Configured instance.
        """
        import os
        return cls(
            name=os.environ.get(f"{prefix}_NAME", "default"),
            enabled=os.environ.get(f"{prefix}_ENABLED", "true").lower() == "true",
            max_items=int(os.environ.get(f"{prefix}_MAX_ITEMS", "100")),
            timeout_seconds=float(os.environ.get(f"{prefix}_TIMEOUT", "30.0")),
        )
    ```

    **Explanation**: This example follows our project conventions by using
    explicit type annotations, comprehensive docstrings, and proper error
    handling. Note the use of logging instead of print statements, and the
    structured return types that facilitate downstream processing.

#### Best Practices

When working with typeguard and type narrowing in the context of advanced type hints, keep these practices in mind:

- Use `Protocol` for structural subtyping instead of abstract base classes where possible
- Define `TypeVar` with meaningful names that indicate the constraint (e.g., `UserT`, `ResponseT`)
- Prefer `Sequence` over `list` in function signatures for input parameters
- Use `TypeGuard` to help type checkers understand custom type narrowing functions

These practices help maintain code quality and reduce the risk of introducing bugs or performance issues related to typeguard and type narrowing.

#### Common Anti-Patterns

Avoid the following anti-patterns when implementing typeguard and type narrowing:

- **Ignoring error conditions**: Always handle potential failures explicitly
  rather than silently swallowing exceptions or returning None.
- **Missing documentation**: Every public function and class must have a
  docstring explaining its purpose, parameters, and return value.
- **Hardcoded configuration**: Extract configuration values into environment
  variables or configuration files rather than embedding them in code.
- **Insufficient testing**: Write tests that cover both the happy path and
  edge cases, including error conditions and boundary values.

These anti-patterns are commonly encountered during code reviews and should
be addressed before merging any changes related to advanced type hints.

#### Integration Notes

When integrating typeguard and type narrowing into existing code, ensure that
the surrounding code follows the same conventions described in this
section. Consistency is more important than any individual rule, so
when in doubt, follow the established patterns in the immediate
codebase context.
